# М3: сравнение моделей (evals уровень 1)

Статус: в работе. Закрывает ТЗ **N7** и уровень «Модель» раздела 10; протокол — `docs/LLM_SELECTION.md`.

## Зачем

Сейчас в `config.yaml` стоит `z-ai/glm-5.3` по итогам **одного** пилотного запроса
(`.scratch/llm-pilot.md`), а базовая линия ТЗ — `deepseek-v3.2`. На защите выбор модели по одному
запросу не защитить. От модели зависят все промпты графа (М4), поэтому сравнение идёт до графа:
переписывать промпты после выбора дороже. ТЗ §10 прямо требует сравнить минимум четыре открытые
модели «на одном наборе задач: корректность tool calling, следование формату, стоимость, латентность».

## Что делаем

1. Набор задач по протоколу LLM_SELECTION §4 (`evals/tasks/model_selection/*.yaml`): A — tool calling
   (20), B — structured output (15), C — роутинг и отказ (20), D — длинный недоверенный контекст
   с инъекциями (10). Инструменты замоканы готовой историей вызовов, кластер не нужен. У каждой задачи
   один правильный ответ — его проверяет код, а не судья.
2. Harness `evals/model_selection.py`, `make eval-models`: 4 основных кандидата × 65 задач × 3 прогона,
   `temperature=0`, таймаут 120 с — провал задачи, ошибки шлюза (429/5xx) — повтор вне статистики,
   стоимость — из `usage.cost` ответа. Шлюз вызывается обычным HTTP: видно, что именно уходит, и не
   нужна новая зависимость.
3. Подсчёт по LLM_SELECTION §6: веса и все четыре дисквалификатора. Таблицы §7.1–7.3 заполняются
   реальными числами, победитель — в `config.yaml`.
4. Схемы `Hypothesis`, `Patch`, `ReviewVerdict`, `IncidentRecord` — `src/k8s_incident_agent/schemas.py`,
   по ARCHITECTURE §5 и MEMORY §3.1. Их же возьмёт граф на М4.
5. `tests/test_model_selection.py`: валидатор задач (размеры блоков, существующие инструменты и схемы,
   аргументы по схеме, факт и инъекция в каждом контексте D) и проверки самих проверок ответов —
   с отрицательными случаями: если проверка ошибается, таблица врёт.

## Что откладывается и почему

- **Блок E (сквозной прогон графа)** — графа ещё нет, он появится на М4. До него латентность и
  стоимость инцидента оцениваются по блокам A–D: p95 одного вызова × 10 вызовов на инцидент
  (LLM_SELECTION R5), медианная цена вызова × 10. Веса §6 не меняются — меняется только источник
  чисел для критериев латентности и стоимости; это оценка, и в таблице она помечена знаком «≈».
  Блок E догоняется после М4 тем же harness'ом.
- **Трассировка в Langfuse** — это М7. Сырые ответы пишутся в `evals/results/model-selection/<время>/`
  (JSON на каждый вызов, в git не попадают), итоговые таблицы — в LLM_SELECTION §7.

## Почему не проще

| Вариант | Почему нет |
|---|---|
| Оставить выбор по пилоту | Один запрос, один инструмент, один прогон — не выбор, а разведка; сам пилот так и сказал |
| Взять готовый бенчмарк (BFCL, τ-bench) | Меряют общее tool calling, а не наши инструменты, схемы и инъекции из логов кластера |
| Один прогон вместо трёх | Разброс — отдельная колонка протокола: нестабильная модель в графе с циклами хуже стабильной |
| Судья-LLM для проверки ответов | В A–D ответы проверяются кодом: имя инструмента, аргументы, валидность схемы, класс. Судья нужен для текста отчёта (М8) |
