# М2.1: две учётки и RBAC (N1)

Статус: реализовано, PR на ревью. Первый кусок этапа М2, карта — `.scratch/m2/spec.md`.

## Зачем

ТЗ **N1**: «диагностический контур имеет ServiceAccount с правами только на чтение. Исполнитель
имеет отдельный SA с правами patch на ограниченный набор ресурсов». Сейчас это только
на бумаге (`docs/ISOLATION.md` §5). Хуже того, код открыт по умолчанию: если
`K8S_RO_KUBECONFIG` не задан, `build_readonly_clients` молча берёт `~/.kube/config`, то есть
**админа kind**. Именно так сейчас и работает `make demo-s1`. Диагност с правами админа —
ровно та ситуация, от которой защищает N1, и узнать о ней было бы не из чего.

## Что делаем

1. **RBAC** в `stand/manifests/base/20-agent-rbac.yaml`: namespace `agent-system`, SA
   `incident-agent-ro` и `incident-agent-rw`. Учётке `-ro` выдаётся ClusterRole: только `get`/`list`
   ресурсов, которые читают семь инструментов, **без `secrets`**. Учётке `-rw` — Role в `payments`
   с `get`/`patch` на deployments, statefulsets и configmaps.
2. **kubeconfig'и**: `up.sh` выпускает токены (`kubectl create token`, 24 ч) и пишет
   `.kube/agent-ro.kubeconfig` и `.kube/agent-rw.kubeconfig` с правами 600. Каталог `.kube/`
   в `.gitignore`.
3. **Конфиг**: пути к kubeconfig — прямо в `config.yaml`, относительно корня репозитория.
   Путь не секрет, переменные окружения для него не нужны.
4. **Отказ без своего kubeconfig (fail-closed)**: путь не задан или файла нет → `K8sClientError`
   с подсказкой `make stand-up`. В `~/.kube/config` код не уходит никогда.
5. **`k8s-agent tool --kubeconfig PATH`**: явная подмена учётки, только в команде ручного вызова
   инструмента. Нужна для демо второго рубежа. Граф (М4) этой опции не увидит.
6. **`make demo-s1` — два рубежа**: поды под учёткой диагноста → Secret под ней же → 403
   (рубеж 1, RBAC) → тот же Secret под админом, «как если бы RBAC настроили шире» →
   `***masked***` (рубеж 2).
7. **`make isolation-test`** (`stand/isolation-test.sh`): проверки ISOLATION §10 №1 и №3 через
   **сами сгенерированные kubeconfig'и**. Итог PASS/FAIL по каждой, код выхода 1 при любом FAIL.
   Запускается и в CI.

## Почему не проще

| Вариант | Почему нет |
|---|---|
| Проверять через `kubectl auth can-i --as=system:serviceaccount:…` | Проверяет правила RBAC, но не то, что агент реально ходит под этой учёткой: `--as` выполняется от админа. Спека М2 (п. 4) прямо запрещает хостовый kubeconfig в проверке |
| Долгоживущий токен через Secret `service-account-token` | Проще, но токен вечный. TokenRequest — стандарт с Kubernetes 1.24; 24 часов хватает на демо, `make stand-up` перевыпускает |
| Role в `payments` и для `-ro` | Evals создают свежий namespace на каждый кейс (EVALS §4.3), а Node — кластерный объект (нужен в S3). Роль на весь кластер, но только чтение и без `secrets` |
| Оставить запасной вариант `~/.kube/config` | Забытая настройка = агент под админом, и никто не узнает. Отказ с понятной ошибкой дешевле |
| Пути к kubeconfig через переменные окружения (как было) | Путь не секрет; контейнер (М2.2) смонтирует файл по тому же относительному пути. Минус две переменные и одна ветка кода |
| `get`+`list`+`watch` на всё, как в черновике ISOLATION §5 | Ни один инструмент не делает `watch` и не перечисляет, например, ConfigMap по кластеру. `get` и `list` разведены по отдельным правилам ровно по вызовам кода |

## Что не входит

- Права исполнителя в namespace'ах evals (EVALS §4.3) — на М4/М8, когда появится executor.
- Kubeconfig с внутренним адресом API-сервера для контейнера — М2.2.

## Проверка

- `make check`: 57 тестов, среди новых — отказ без kubeconfig (оба контура, до вызова SDK),
  относительные пути, подмена через `--kubeconfig` в CLI.
- Живой kind: `make isolation-test` — 24 из 24 PASS; `make demo-s1` показывает отказ RBAC
  и `***masked***`; grep значения Secret с `COLUMNS=100000` — 0; все семь инструментов под
  учёткой диагноста — `ok`; без файла kubeconfig — ошибка с подсказкой `make stand-up`.
- Тесты на тест: учётке `-ro` выдали `secrets` — 3 FAIL, утечки при этом нет (рубеж 2);
  выдали `pods/exec` — 2 FAIL; сломали маскирование `data` — 1 FAIL.
- CI зелёный.

## Ревью (независимый субагент) и что исправлено

1. `can-i get pods/log` / `create pods/exec` kubectl читает как «под с именем log/exec» —
   проверки подресурсов ничего не проверяли. Теперь `--subresource=…`, плюс attach и portforward.
2. Значение Secret искалось только открытым текстом, а `data` приходит в base64: сломанное
   маскирование `data` прошло бы незамеченным. Теперь ищутся обе формы (тест и CI).
3. Роль шире заявленного «по факту кода» (`list configmaps` по кластеру и др.) — `get` и `list`
   разведены по отдельным правилам.
4. `patch deployments` у исполнителя косвенно открывает Secret'ы namespace — записано честно
   в ISOLATION §9 и DEFENSE; барьер — белый список путей патча (М4).
5. `admin.kubeconfig` лежал в `.kube/` рядом с токенами агента — убран: демо берёт
   `~/.kube/config`, `isolation-test` — временный файл.
6. Истёкший токен: `isolation-test` и ответ 401 подсказывают `make stand-up`.
7. Мелочи: `uv run --project`, разбор пар через `:` заменён функцией, права `.kube` 700,
   `rm -f` перед записью kubeconfig, тильда в путях конфига.

## Найдено по ходу (отдельный кусок)

Для S1 это главное свидетельство — чинится следующим PR.
