# CI на GitHub Actions

Статус: реализовано, PR на ревью. Мержить после PR #1: без исправления маскирования
проверка утечки в CI справедливо упадёт.

## Зачем

1. **ТЗ раздел 10:** evals запускаются «локально командой и в CI на каждый PR». Пока у
   репозитория не было remote, в `docs/DEFENSE.md` это значилось открытым расхождением. С 2026-10-09
   remote есть (`fastrapier/k8s-agent`), и закрыть пункт можно по-настоящему.
2. **ТЗ N6 и правило roadmap:** этап закрыт, только если команда отработала на чистом клоне.
   Ноутбук автора чистым клоном не является. Раннер GitHub — является.
3. **Работа кусками через PR:** каждый следующий PR получает автоматическую галочку, и ревьюер
   видит, что линт, тесты и стенд проходят, не запуская ничего руками.

## Что делаем

Один файл `.github/workflows/ci.yml`, две задачи:

- `check` — `uv sync --locked` + `make check` (линт, юнит-тесты). `--locked` падает, если
  `uv.lock` разошёлся с `pyproject.toml`, — это тоже N6.
- `stand` — kind v0.33.0 (та же версия, что у автора), `make stand`, `make demo-s1`, grep
  значения Secret по выводу. Повторяет приёмку М1 на каждом PR.

Плюс документы: `CLAUDE.md` и HANDOFF больше не говорят «remote нет», `docs/DEFENSE.md` —
два ответа для защиты и уточнённое расхождение (системные evals в CI появятся на М8).

## Почему не проще

- **Только `check`, без стенда.** Юнит-тесты не ловят то, что ломается на живом кластере: утечку
  через аннотацию нашёл только живой прогон. Стенд в CI — единственный способ проверить N6
  на чистой машине.
- **`helm/kind-action` вместо curl.** Ещё одна сторонняя зависимость ради двух строк. Скачать
  бинарник — прозрачнее и легко объяснить.
- **Системные evals сразу.** Их ещё нет (М8), и им нужен токен шлюза в секретах GitHub.

## Проверка

- Проверка утечки должна уметь падать: локально на коде из `main` с `COLUMNS=100000` — 1 совпадение,
  на ветке с исправлением — 0. Без `COLUMNS` — 0 в обоих случаях (перенос строк `rich`).
- Первый прогон workflow на этом PR: обе задачи зелёные.
