# М6: эпизодическая память — прошлые инциденты (F8, S5)

Статус: реализовано, PR. Срок защиты — 2026-10-13, этап одним PR, сначала ширина.

## Зачем

ТЗ F8: после завершения инцидент записывается в долгосрочную память (симптомы, причина, фикс, затронутые
объекты, дата). S5: при повторе поломки агент находит прошлый случай и ссылается на него в отчёте.
Приёмка roadmap: `make demo-s5` — агент находит прошлый инцидент и ссылается на него в отчёте.

Без этого каждый инцидент начинается с нуля. Инженер, который чинил ту же поломку месяц назад, видит
в отчёте ссылку и то, чем текущий случай отличается от прошлого. На защите это единственное место, где
видно, что агент учится на прошлом, а не только рассуждает.

## Что делаем

1. **`memory.py` — хранилище.** SQLite `data/memory.sqlite`, таблица `incidents` по схеме MEMORY §3.1 и
   `incidents_fts` (FTS5, `unicode61 remove_diacritics 2`). Том `agent-data` в контейнере уже смонтирован в
   `/app/data`, поэтому память переживает перезапуск контейнера.
   - `write(record, ...) -> id` — id вида `inc-2026-10-10-001`. Дубль (тот же namespace, объекты и фикс)
     не плодится: старая запись помечается `superseded_by`.
   - `search(query, namespace=None, limit=3)`. Сначала фильтры, потом ранжирование: namespace, без
     `superseded_by`, без `unresolved`. Ранжирует BM25 по FTS5, у записей старше 180 дней score вдвое
     ниже. Запрос разбивается на слова, каждое слово ищется как префикс (`слово*`) — это заменяет
     стемминг для русского.
   - `seed(path)` — загрузка фикстуры прошлых инцидентов из YAML, повторная загрузка безопасна.
2. **Узел `remember` (memory_writer) в графе** после `execute` / `propose`, до `report`. Запись собирается
   из состояния кодом, без отдельного вызова модели:
   - симптомы — жалоба;
   - причина — главная гипотеза, она уже прошла ревьюер;
   - фикс — рекомендация и патч;
   - объекты — цель патча;
   - `fix_applied` и `outcome` — из результата исполнителя.

   Каждое текстовое поле проходит через `mask_text`, длина ограничена. Если ревьюер не принял гипотезу или
   патч не применён, запись получает `outcome=unresolved`: она сохраняется, но в поиск не попадает.
3. **Поиск похожих в `analyze`.** Перед первым анализом — `search(query, namespace)`, кандидаты (≤ 3)
   попадают в промпт аналитика. Модель отмечает для каждого, тот ли это класс поломки и чем он отличается.
   Это и есть LLM-переранжирование из MEMORY §3.3, только внутри вызова, который всё равно делается. Код
   отбрасывает ссылки на id, которых не было среди кандидатов.
4. **Отчёт.** Раздел «Похожие инциденты»: id, дата, прошлая причина и фикс, отличие от текущего случая.
   Строка «Записано в память: inc-…».
5. **CLI и make.** `k8s-agent memory list | search | seed`. `make demo-s5` загружает фикстуру и запускает
   жалобу S1. В фикстуре прошлый S1 (месяц назад, тот же класс) и «похожий, но другой» (checkout,
   OOMKilled), чтобы было видно, что агент различает их (EVALS §S5).

## Почему не проще

| Вариант | Почему нет |
|---|---|
| Не делать память, показать S5 словами | F8 и S5 — пункты ТЗ, резать нельзя |
| Писать всю историю прогона (JSON состояния) | В поиск попадёт шум. Сырые логи в памяти запрещены (MEMORY §3.2): там могут быть персональные данные |
| Отдельный вызов модели для извлечения записи | Причина уже структурирована моделью в `analyze` и проверена ревьюером. Второй пересказ — новая возможность ошибиться и плюс один вызов |
| Отдельный узел переранжирования | Аналитик всё равно читает кандидатов. Пометка «тот же класс / чем отличается» — одно поле в его ответе |
| Mem0 / LangMem / векторная БД | MEMORY §6: единица памяти — структурированный инцидент, а не факт из переписки. Нужны внешние сервисы или эмбеддинги через API (закрыты на шлюзе) |

## Упрощения против MEMORY.md (записать в DEFENSE)

- **Нет эмбеддингов bge-m3 и RRF.** Веса модели около 2,2 ГБ плюс torch, а лимит контейнера 512 МиБ
  (`docker-compose.yml`). Записей десятки, ложные совпадения по общим словам гасят фильтр по namespace и
  суждение аналитика «тот же класс?». Путь апгрейда: таблица `incident_vectors` по MEMORY §3.1 и канал
  косинуса в RRF; интерфейс `search` не меняется.
- **Нет отдельного ревью записи.** Используется вердикт ревьюера графа: что он не принял, хранится как
  `unresolved` и в поиск не попадает.
- **Чекпоинты графа уже в SQLite** (М4). Свидетельства живут в памяти процесса, как и раньше. Их переезд не
  нужен ни для S5, ни для F8.

## Проверка

- Юнит-тесты `tests/test_memory.py`:
  - запись и поиск;
  - фильтр namespace;
  - `unresolved` не находится;
  - дубль помечает старую запись `superseded_by`;
  - старая запись ранжируется ниже;
  - маскирование токена в поле;
  - `seed` идемпотентен.
- Граф на FakeLLM:
  - после S1 есть запись `resolved` с id в отчёте;
  - при отказе человека запись `unresolved`;
  - кандидат из памяти попадает в отчёт, выдуманный id отбрасывается.
- Вживую: `make demo-s5` — в отчёте ссылка на прошлый S1 и отличие от OOM-случая.
- `make isolation-test` — память не открывает новых путей наружу.
