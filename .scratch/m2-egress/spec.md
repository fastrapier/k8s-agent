# М2.3: сеть агента — только LLM-шлюз и API-сервер (N2)

Статус: реализовано, PR на ревью. Третий и последний кусок М2, карта — `.scratch/m2/spec.md`.

## Зачем

ТЗ **N2**: «сетевой доступ только к LLM API и API-серверу кластера». Угроза T5 из ISOLATION:
код или зависимость отправляет собранные данные (логи, манифесты кластера) на сторонний адрес.
После М2.2 контейнер жил в docker-сети `kind`, у которой есть выход наружу, — ограничения не было.

## Что делаем

1. Внутренняя сеть `agent-egress`: `internal: true` (нет маршрута наружу) и `inhibit_ipv4` (нет адреса
   на мосту — иначе через него виден хост Docker).
2. `egress-proxy` (tinyproxy на alpine, `stand/egress-proxy/`): стоит в двух сетях, пропускает только
   `CONNECT` к парам «имя:порт» из `allowlist`, обычный HTTP запрещён. Без root, read-only, без capabilities.
3. Агент: только сеть `agent-egress`, `HTTPS_PROXY` в окружении. Код агента не меняется — клиент
   `kubernetes` и httpx читают переменную сами.
4. `make isolation-test`, раздел «№5 Сеть»: восемь замеров, включая слушатель на хосте с контролем.
   `down.sh` останавливает прокси вместе с кластером.
5. ISOLATION §3 описывает реализацию вместо черновика; DEFENSE — ответы; `name:` у compose-проекта,
   чтобы имена сетей не зависели от имени каталога клона.

## Почему не проще

| Вариант | Почему нет |
|---|---|
| Подключить ноду kind во внутреннюю сеть, прокси только для LLM | Агенту открылась бы вся нода: kubelet, NodePort-сервисы. Прокси пропускает ровно `API-сервер:6443` |
| iptables/nftables-правила на хосте | На macOS Docker живёт в VM, правила хоста туда не доходят; в CI — другие права. Внутренняя сеть + прокси работают одинаково везде |
| Squid вместо tinyproxy | Тоже подходит, но требует записываемых каталогов кеша и логов. tinyproxy — 10 строк конфига, запускается read-only |
| Envoy | Мощнее, но конфиг на порядок длиннее; для allow-list из двух имён избыточен |
| L4-реле (socat) с сетевыми алиасами | Встроенный DNS Docker отдаёт контейнеру его же алиасы: реле, резолвя имя шлюза, замкнулось бы на себя. Пришлось бы писать IP — хрупче |
| Хост LLM-шлюза из `local.env` в allow-list автоматически | Сетевая граница должна меняться правкой в репозитории, видимой в диффе |

## Проверка

- `make isolation-test`: раздел №5 — 8 PASS, всего 40 из 40.
- Тесты на тест: агент в сети `kind` без прокси — 4 FAIL; `example.com` в allow-list — FAIL;
  старый конфиг прокси (фильтр по имени + `ConnectPort`) — 2 FAIL; сеть без `inhibit_ipv4` — FAIL.
- Инструменты из контейнера работают через прокси (в логе прокси — `CONNECT …:6443`).
- CI зелёный.

## Ревью (независимый субагент) и что исправлено

1. **Обычный HTTP обходил ограничение портов**: `GET http://нода:10256/healthz` → 200, шлюз на 6443
   разрешался перекрёстно. → `FilterURLs On`, allow-list из пар «имя:порт».
2. **Адрес моста internal-сети — это хост Docker**, агент доставал до его сервисов напрямую.
   → `inhibit_ipv4`; проверка слушателем на хосте с контролем из сети `kind`.
3. Тест пересобирал только образ агента — проверялся старый прокси. → `compose build` всех сервисов.
4. Классификатор засчитывал любой таймаут как «недоступно» и не отличал 403 прокси от 403 адресата.
   → `ENETUNREACH`, `socket.gaierror`, заголовок `Server: tinyproxy`.
5. Лишние строки конфига (`Allow 0.0.0.0/0`, умолчания) убраны; `down.sh` останавливает прокси.
6. Остаточный риск domain fronting записан в ISOLATION §3.
