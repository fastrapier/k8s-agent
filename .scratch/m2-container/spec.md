# М2.2: контейнер агента (N2)

Статус: реализовано, PR на ревью. Второй кусок М2, карта — `.scratch/m2/spec.md`.

## Зачем

ТЗ **N2**: «агент запускается в контейнере без root, с read-only файловой системой, без
capabilities». ТЗ §14 перечисляет `docker-compose.yml` среди результатов. До этого куска агент
работал только процессом на хосте — с правами пользователя ноутбука, его файлами и его сетью.
Агент читает недоверенные данные (логи чужих приложений) и подаёт их в LLM; если через
зависимость или prompt injection он начнёт делать лишнее, контейнер ограничивает, что он может
сделать с машиной (ISOLATION, угроза T4).

## Что делаем

1. `Dockerfile`: две стадии (uv собирает окружение по `uv.lock`, в образ идут только `.venv` и
   `config.yaml`), `USER 10001`, базовые образы прибиты дайджестом.
2. `.dockerignore`: allow-list — в контекст сборки не попадают `local.env` и `.kube/`.
3. `docker-compose.yml`: `user: 10001`, `read_only`, `cap_drop: ALL`, `no-new-privileges`,
   лимиты, `tmpfs /tmp noexec`, один том — kubeconfig диагноста только на чтение, сеть `kind`.
4. `up.sh` выпускает `.kube/agent-ro.container.kubeconfig`: тот же диагност, но API-сервер по имени
   ноды kind в docker-сети.
5. `make agent-build`, `make agent-tool`; `make isolation-test` — раздел «№4 Контейнер».
6. ISOLATION §4 описывает реальные файлы вместо черновика; DEFENSE — ответы.

## Почему не проще

| Вариант | Почему нет |
|---|---|
| Одна стадия, `COPY . .` | В образ уехали бы uv, исходники, кеши — и, без `.dockerignore`, `local.env`. Две стадии — стандартный приём, объясняется одной фразой |
| Свой `seccomp.json` (как в черновике ISOLATION) | Профиль Docker по умолчанию уже режет опасные вызовы; свой профиль надо сопровождать, а для агента без root и capabilities выигрыш минимальный |
| `docker run` с флагами вместо compose | Compose — результат по ТЗ §14, и все ограничения видны в одном файле с комментариями |
| Тома `/data`, скиллы, `env_file` сразу, как в черновике | Им пока нечего читать и писать. Добавляются вместе с кодом, которому нужны (М4–М6) |
| Тег образа вместо дайджеста | Тег перезаписывается; через месяц тот же Dockerfile собрал бы другой образ (N6) |
| Проверять запись в `/app` и `CapEff` | Обе проверки проходят и без ограничений: `/app` не наш по правам, `CapEff` у не-root нулевой. Проверяем `/var/tmp` и `CapBnd` |

## Что не входит

Ограничение сети — следующий кусок (М2.3). Пока у контейнера через сеть `kind` есть выход наружу.

## Проверка

- `make isolation-test`: раздел №4 — 8 PASS (6 замеров + 2 вызова инструмента); вместе с RBAC — 32.
- Тесты на тест: без ограничений и с `user: root` — 4 FAIL; `docker.sock` в `/docker.sock` и kubeconfig
  без `:ro` — FAIL списка монтирований; `seccomp:unconfined` — FAIL; без файла kubeconfig compose
  падает с ошибкой, а не создаёт каталог на его месте.
- Контекст сборки — 4 пути; в образе нет uv и исходников; пиковая память агента ~90 МиБ.
- CI: первая версия упала — см. ниже; после исправления — результат в PR.

## Ревью (независимый субагент) и CI

1. **CI красный:** на Linux uid 10001 не мог прочитать kubeconfig с правами 600 (Docker Desktop на
   macOS права не проверяет). Файл контейнера — 644, от хоста его закрывает каталог `.kube` (700).
2. Короткая запись тома создавала каталог на месте отсутствующего файла — длинная запись с
   `create_host_path: false`, плюс проверка файла в `make agent-tool`.
3. `CapEff: 0` упасть сама не может — убрана.
4. Проверка одного пути к `docker.sock` — заменена списком монтирований; добавлен `Seccomp: 2`.
5. `COLUMNS=… compose run` не доходил до контейнера — `-e COLUMNS=…`.
6. `noexec` описан честно (Docker ставит его сам, интерпретатор он не останавливает); `/tmp:size=64m`.
7. `mem_limit: 2g` «под bge-m3» — без основания; 512 МБ от замера, пересмотр на М6.
8. Мелочи: убран `PYTHONDONTWRITEBYTECODE`, прибит `hatchling==1.32.4`, `probe` не роняет скрипт молча.
