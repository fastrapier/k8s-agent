# М4: граф агента (F1–F7, F10)

Статус: реализовано, PR на ревью. Срок защиты — 2026-10-13, поэтому этап одним PR.

## Зачем

До М4 агента не было: инструменты, стенд, изоляция и выбранная модель — но ничего, что принимает
жалобу инженера и доводит её до исправления. ТЗ §5: оркестратор, диагност, аналитик, ревьюер, подтверждение
человеком, исполнитель; приёмка roadmap — `make demo-s1` доходит до патча, требует подтверждения,
применяет и проверяет; `make demo-s6` — отказ без единого вызова инструментов.

## Что сделано

- `graph.py`: classify → plan → diagnose (цикл с инструментами) → analyze → review (≤ 2 итераций) →
  propose → approval (`interrupt()`) → execute → report; out_of_scope → отказ; runbook_qa → ответ.
- `executor.py`: белый список kind/namespace/путей, снятие идентифицирующих полей, применение учёткой
  исполнителя, пост-проверка раскатки, команда отката при неудаче.
- `llm.py`: общий клиент шлюза (тот же, что в сравнении моделей).
- `k8s-agent run`: ход графа по узлам, патч и вопрос человеку, отчёт F10; `--model`.
- Контейнер: токен шлюза, kubeconfig исполнителя, том для чекпоинтов — агент работает в изоляции М2.
- Тесты: граф на поддельной модели (маршруты, подтверждение, бюджеты, инварианты, деградация),
  белый список исполнителя.

## Почему не проще

| Вариант | Почему нет |
|---|---|
| Один большой промпт с инструментами вместо графа | ТЗ требует граф с ревью и подтверждением; инварианты проверяет код, а не модель |
| Подтверждение полем в состоянии | Модель могла бы его выставить сама; `interrupt()` — только внешний resume |
| LangChain-модели вместо своего клиента | Лишний слой; сравнение моделей должно мерить тот же код, что работает в агенте |
| Применять патч от учётки диагноста | N1: запись — отдельная учётка и отдельный модуль |
