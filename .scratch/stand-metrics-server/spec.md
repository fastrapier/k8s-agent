# Стенд: metrics-server; ingress-controller осознанно не ставим

Статус: реализовано, PR на ревью. Закрывает два решения из HANDOFF §5, открытых с 2026-09-29.

## Зачем

- **metrics-server.** `k8s_top` — один из семи инструментов ТЗ раздела 6. Без metrics-server
  он на стенде всегда отдаёт `degraded`, и показать его вживую нельзя. Автор решил ставить.
- **ingress-controller.** Предполагалось, что он даст «настоящий 502» в S2. Проверка 2026-10-09
  показала обратное: ingress-nginx на сервис без endpoints (поломка S2) отвечает **503**;
  502 получается только при другой поломке (неверный `targetPort`). Проект ingress-nginx
  заархивирован с марта 2026. Автор решил не ставить. Тогда заготовка под контроллер в
  `kind.yaml` (метка `ingress-ready`, проброс 8080/8443) — лишняя сложность и риск занятого порта.

## Что делаем

1. `up.sh`: metrics-server v0.9.0 из релизного манифеста + `--kubelet-insecure-tls`, без
   дублирования флага при повторном запуске; ожидание `rollout status`.
2. `status.sh`: строка о наличии метрик.
3. `kind.yaml`: убрана заготовка под ingress.
4. Комментарии S2, README стенда, `docs/DEFENSE.md` — почему так.
5. CI: `k8s_top` на чистом раннере возвращает `ok`.

## Почему не проще

- **metrics-server из своего YAML в репозитории.** 200 строк чужого манифеста, которые
  придётся обновлять руками. Ссылка на релиз с прибитой версией — то же N6, но короче.
- **`serverTLSBootstrap` + одобрение CSR вместо `--kubelet-insecure-tls`.** Правильнее для
  продакшена, но это патч kubeadm и ручное одобрение сертификатов. Для локального стенда
  излишне; ограничение записано в README.
- **Оставить заготовку под ingress «на всякий случай».** Решение принято, заготовка ничего
  не даёт, а занятый порт 8080 ломает `kind create cluster`.
