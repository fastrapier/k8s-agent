# Демо-стенд k8s-incident-agent

Кластер kind и набор «сломанных» манифестов, воспроизводящих сценарии **S1–S4** из `docs/TZ.md`
(раздел 2). Этап М1 плана из `.scratch/roadmap.md`. Закрывает требование N6: стенд поднимается
одной командой.

> **Статус проверки на 2026-10-05:** `make stand` и `make demo-s1` прошли на живом
> kind-кластере (kind v0.33.0, Docker 29.8.1). Все S1–S4 достигли целевого состояния,
> здоровый `checkout` остался 2/2 Ready. При первом прогоне обнаружили и исправили утечку
> значения Secret через аннотацию `last-applied-configuration`; повторное демо показало
> только `***masked***`.

## Быстрый старт

```bash
./up.sh          # кластер + namespace payments + здоровый Deployment
./break.sh all   # внести все поломки S1–S4 и дождаться, пока они проявятся
./status.sh      # что поднято и в каком состоянии
./clean.sh all   # снять поломки (удалить namespace), кластер остаётся
./down.sh        # снести кластер
```

Отдельный сценарий: `./break.sh s1`, снять его же: `./clean.sh s1`.

Контекст kubectl — `kind-k8s-incident-agent`, namespace — `payments`. Все скрипты прибиты к этому
контексту явным `--context`, поэтому в чужой кластер не попадут даже при неверном `current-context`.

## Кластер: 3 ноды и почему именно столько

`kind.yaml` — 1 control-plane + 2 worker.

- **Не одна нода.** На control-plane висит taint `node-role.kubernetes.io/control-plane:NoSchedule`.
  При единственной ноде планировщик писал бы «0/1 nodes are available», и сценарий S3 читался бы как
  артефакт стенда. С тремя нодами событие выглядит как в проде:
  «0/3 nodes are available: 1 node(s) had untolerated taint, 2 node(s) didn't match Pod's node
  affinity/selector». Плюс здоровые поды реально размазываются по двум воркерам, что видно в
  `kubectl get pods -o wide`.
- **Не больше трёх.** Каждая нода — отдельный контейнер Docker, примерно 0.5 ГБ RSS на ноутбуке.
  Четвёртая нода не добавляет ничего ни одному из сценариев S1–S4.

Версия ноды зафиксирована тегом `kindest/node:v1.31.0`. Дайджест намеренно не прибит: правильный
дайджест зависит от версии `kind` на машине и берётся из её release notes. Если образ не тянется —
закомментируйте строки `image:` в `kind.yaml`, kind подставит свой дефолтный образ.

## Что покрыто

| Сценарий | Объект | Поломка | Симптом | Ожидание в `break.sh` |
|---|---|---|---|---|
| **S1** CrashLoopBackOff | `Deployment/api` | не задана переменная окружения `DB_PASSWORD` (потеряли `secretKeyRef` при релизе) | `0/1 CrashLoopBackOff`, растут RESTARTS; в логах `FATAL: environment variable DB_PASSWORD is not set`; в `describe` — Exit Code 1 | `restartCount >= 2` |
| **S2** 502 после релиза | `Ingress/web` → `Service/web` → поды | `selector` сервиса остался `version=v1`, поды после релиза помечены `version=v2` | у сервиса нет ни одного endpoint, при этом поды 2/2 Ready — классическая ловушка «поды живые, а сервис не работает» | поды Ready **и** endpoints = 0 |
| **S3** не раскатывается | `Deployment/reports` | в релизе v2 добавлен `nodeSelector: disktype=nvme`, такой метки нет ни на одной ноде | 5 подов: 3 Running (старый RS) + 2 Pending; `rollout status` не завершается; событие `FailedScheduling` | подов в Pending `>= 2` |
| **S4** Job не завершается | `Job/db-migrate` | init-контейнер бесконечно ждёт несуществующий сервис `payments-db:5432` | `COMPLETIONS 0/1`, под в `Init:0/1`, 0 рестартов, в логах init-контейнера бесконечное «not reachable yet» | init-контейнер в состоянии Running |

Вариации взяты из `docs/EVALS.md`, раздел 4.2 — по одной на сценарий.

Плюс два объекта без поломки:

- **`Deployment/checkout`** — здоровый, 2/2 Ready. Контраст для защиты: видно, что агент отличает
  рабочую нагрузку от сломанной и не «находит» проблему там, где её нет. Именно у него на месте тот
  самый блок `DB_PASSWORD` из `secretKeyRef`, которого не хватает `api` из S1.
- **`Secret/payments-db`** со значением `s3cr3t-do-not-leak` — для демонстрации маскирования
  (ТЗ N1, `docs/ISOLATION.md` раздел 6). Значение выбрано заметным и грепаемым: на защите
  показываем, что `k8s_get_manifest` отдаёт `***masked***`, а
  `grep -r s3cr3t-do-not-leak` по выводу инструментов, по SQLite и по трейсу не находит ничего.
  Вывод CLI грепать только с `COLUMNS=100000`: иначе `rich` переносит строки по 80 символов,
  разрезает значение, и grep не найдёт его даже при утечке.

## Почему `break.sh` ждёт, а не просто `apply`

Сразу после `kubectl apply` под ещё в `ContainerCreating`, а Job вообще не создал под. Демо в этот
момент показывает пустоту. Поэтому каждый сценарий дожидается **своего симптома** — это та же идея,
что поле `wait_for` в `case.yaml` (`docs/EVALS.md`, раздел 4.1), только в bash.

У ожидания есть таймаут (`STAND_WAIT_TIMEOUT`, по умолчанию 180 с). При его истечении скрипт не
висит вечно, а печатает поды, последние события и состояние нод, после чего выходит с кодом 1.

S3 внутри `break.sh` делает два шага: сначала раскатывает рабочую версию `reports` и ждёт 3/3 Ready,
и только потом накатывает патч с `nodeSelector`. Без первого шага в Pending ушли бы все поды,
а в ТЗ сценарий сформулирован как «зависли 2 из 5». Связка `replicas=3, maxSurge=2,
maxUnavailable=0` даёт ровно эту картину детерминированно.

## Сколько занимает

Первый живой прогон на MacBook с Docker Desktop (2026-10-05). Повторный подъём и очистка
пока не измерялись:

| Шаг | Первый раз | Повторно (образы в кеше) |
|---|---|---|
| `up.sh` — создание кластера из 3 нод | **75 с** | не измерено |
| `break.sh all` | **27 с** | не измерено |
| `clean.sh all` | не измерено | не измерено |
| `down.sh` | не измерено | не измерено |

Из чего складывается `break.sh all`: S1 упирается в backoff CrashLoop (рестарты идут через 0 с,
10 с, 20 с — значит `restartCount >= 2` достижим примерно за 30 с), S2 — в `initialDelaySeconds: 2`
плюс период readiness-пробы, S3 — в полную раскатку исходной версии перед поломкой, S4 — в старт
init-контейнера.

Ускорение, заложенное осознанно: **вся нагрузка стенда работает на одном образе `busybox:1.36`**
(~2 МБ). Один pull на ноду вместо четырёх разных образов. `httpd` из busybox закрывает и
readiness-пробы, и роль «веб-сервиса» в S2.

## Что стенд намеренно не делает

- **Не ставит ingress-controller.** В S2 объект `Ingress` есть, но настоящего HTTP-502 из браузера
  не будет: контроллера некому обработать правило. Симптом воспроизводится на уровне объектов —
  пустой EndpointSlice у сервиса, на который ссылается Ingress, а это ровно то, что читает агент
  через `k8s_describe`/`k8s_list_pods`. Установка ingress-nginx — это ещё один pull на ~150 МБ и
  минута ожидания на каждом подъёме стенда. В `kind.yaml` уже проставлены метка `ingress-ready=true`
  и проброс портов 80/443 на 8080/8443, так что доставить контроллер при желании можно одной
  командой, ничего не переделывая.
- **Не ставит metrics-server.** Инструмент `k8s_top` из ТЗ раздела 6 помечен «при наличии
  metrics-server» — на этом стенде он будет отдавать ошибку, и это ожидаемое поведение.
- **Не создаёт ServiceAccount и RBAC.** Это этап М2 (`docs/ISOLATION.md`, раздел 5).
- **Не содержит `case.yaml` и каталог `evals/`.** Это этап М8. Сейчас стенд ручной; вариации
  поломок и условия ожидания совпадают с будущими кейсами, чтобы М8 переиспользовал эти манифесты.

## Что проверить при первом запуске

Первый прогон выполнен 2026-10-05:

1. `kind`, `kubectl` и работающий Docker доступны; образ `kindest/node:v1.31.0` загрузился.
2. Ожидания S1–S4 уложились в 180 с; S1 — 18 с, S2 — 3 с, S3 — 0 с после патча,
   S4 — 3 с. Полный `break.sh all` — 27 с.
3. `status.sh` показал «сломано как надо» для всех четырёх сценариев и Ready=2 у `checkout`.
4. `make demo-s1` подтвердил CrashLoopBackOff и маскирование Secret после исправления аннотаций.

## Файлы

```
stand/
  kind.yaml                                  конфиг кластера: 1 control-plane + 2 worker
  lib.sh                                     общие функции скриптов: логи, ожидание с таймаутом, проверки состояния
  up.sh                                      поднять кластер (идемпотентно) + namespace + базовые объекты
  break.sh                                   внести поломку [s1|s2|s3|s4|all] и дождаться симптома
  clean.sh                                   снять поломку: сценарий точечно или namespace целиком
  status.sh                                  состояние стенда и вердикт по каждому сценарию
  down.sh                                    снести кластер
  manifests/
    base/00-namespace.yaml                   namespace payments
    base/10-secret.yaml                      Secret payments-db с маркером s3cr3t-do-not-leak
    base/30-deployment-checkout.yaml         здоровый Deployment + Service (контрольный образец)
    s1-crashloop/deployment.yaml             S1: Deployment api без DB_PASSWORD + Service
    s2-502/deployment.yaml                   S2: здоровые поды web с меткой version=v2
    s2-502/service.yaml                      S2: поломка — selector сервиса застрял на version=v1
    s2-502/ingress.yaml                      S2: верхнее звено цепочки Ingress → Service → Endpoints
    s3-pending/10-deployment.yaml            S3: исходная рабочая версия reports (3 реплики)
    s3-pending/20-break-nodeselector.yaml    S3: поломка — patch с nodeSelector disktype=nvme
    s4-stuck-job/job.yaml                    S4: Job с init-контейнером, ждущим несуществующий сервис
```
