# Сценарий защиты (живое демо, ~15 минут)

Одна команда — `make demo`: шесть шагов подряд, подтверждение патча вводится руками («y»).
Отрепетировано 2026-10-10: три прогона подряд без единой ошибки, 1.7–2.3 минуты чистого времени на весь
сценарий; S1 и S5 — 32–60 с каждый, оба патча применены, на шаге 5 найдены прошлые случаи того же класса.
Память демо начинается с чистого листа (прежняя откладывается в `data/memory.<время>.sqlite`). Ниже — что
показывает каждый шаг, что говорить и чем подстраховаться, если что-то пойдёт не так.

## За 30 минут до начала

```bash
open -a Docker                      # Docker Desktop
make stand-status                   # все четыре сценария: «сломано как надо»
make check                          # линт и тесты зелёные
make obs-up && make metrics &       # Grafana на http://127.0.0.1:3000 (по желанию)
```

Если стенд «поплыл» после перезапуска Docker: `make stand-break SCENARIO=all` (около 2 минут).
Если кластера нет совсем: `make stand` (около 3 минут на чистой машине).

## Шаги `make demo`

| # | Что на экране | Что говорить | Время |
|---|---|---|---|
| 1 | `stand-status`: S1–S4 «сломано как надо» | стенд — kind, четыре поломки из ТЗ §2, вносятся одной командой; причина поломки — только в комментарии манифеста, агенту не видна | 15 с |
| 2 | S6 «напиши стих» → вежливый отказ | отказ — фиксированный текст, ни одного вызова инструментов и модели после классификации | 3 с |
| 3 | S1: скилл crashloop-diagnosis, план, 4–6 вызовов инструментов, гипотеза со ссылками ev-NNN, ревью ok, **патч и вопрос «Применить?»** → «y» → applied, раскатка завершена | см. «Ключевые реплики» ниже | 30–45 с |
| 4 | `trace --last`: шкала узлов, вызовов модели и инструментов с латентностью и ценой | так нашли две главные проблемы: рассуждение модели до 74 с на узел и зависание `propose` | 5 с |
| 5 | S5: та же жалоба после повторной поломки → «Похожие инциденты»: прошлый S1 — тот же класс, OOM-случай — другой | память — SQLite FTS5; тот ли это класс, решает аналитик, выдуманный id отбрасывает код | 35–45 с |
| 6 | `agent_runs_total`, длительность и цена из `/metrics` | метрики считаются из трейсов при скрейпе — CLI живёт 30 с, pushgateway не нужен | 3 с |

## Ключевые реплики к шагу 3 (S1)

- **Почему агенту можно доверить патч?** Он его не применяет. `k8s_patch` у диагноста нет; применение —
  отдельный модуль под отдельной учёткой; перед ним `interrupt()`, продолжить который может только человек.
- **Откуда имя ключа Secret, если Secret читать нельзя?** Из манифеста здорового соседа `checkout`: там
  видно, что `DB_PASSWORD` берётся из `payments-db/password`. Это шаг скилла crashloop-diagnosis.
- **Что, если модель ошиблась с патчем?** Белый список путей, запрет `null` и `$`-директив, патч только к
  прочитанному объекту, сверка uid/generation перед применением, пост-проверка раскатки.

## После основного сценария (по вопросам комиссии)

```bash
make isolation-test                 # 40 проверок изоляции: RBAC, контейнер, сеть (~2 мин)
make demo-s1-container              # тот же S1 из изолированного контейнера
make alerts-check                   # promtool: правила валидны, алерт стреляет на синтетике
uv run k8s-agent memory list        # что агент запомнил
```

Отчёт системных evals — `docs/EVALS_REPORT.md`; сравнение моделей — `docs/LLM_SELECTION.md` §7.

## Если что-то сломалось во время демо

| Симптом | Что делать |
|---|---|
| LLM-шлюз не отвечает (в отчёте «модель не ответила») | показать сохранённый полный прогон `docs/demo/make-demo.txt` (и отдельные S1, S5, трейс); объяснить деградацию: граф не падает, отчёт с разделом «Ограничения» |
| Модель не предложила патч на S1 | это поведение, а не сбой: модель осторожна, если не видит ключ Secret; повторить запуск — прогоны недетерминированы, в evals патч предлагается в большинстве случаев |
| S1 уже починен (под Running) | `make stand-break SCENARIO=s1` (15 с) |
| GitHub / интернет недоступен | ничего не нужно: демо локальное, наружу ходит только запрос к LLM-шлюзу |
