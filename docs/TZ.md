# ТЗ: мультиагентная система диагностики инцидентов в Kubernetes

Рабочее название: **k8s-incident-agent**. Версия документа: 0.1, 2026-09-28.

## 1. Назначение

Система принимает от инженера описание проблемы в кластере Kubernetes на естественном языке,
самостоятельно собирает факты через инструменты, сопоставляет их с накопленной памятью об
инцидентах и runbook'ами, формулирует корневую причину и предлагает исправление.
Любое изменяющее действие в кластере выполняется только после явного подтверждения человеком.

Что система **не** делает в рамках v1:

- не выполняет автономных мутаций без подтверждения;
- не работает с несколькими кластерами одновременно;
- не заменяет систему алертинга, а подключается после того, как инцидент уже замечен.

## 2. Пользователи и сценарии

Пользователь: DevOps/SRE-инженер, работающий с кластером через CLI или чат.

Основные сценарии (используются и как eval-кейсы):

| # | Запрос пользователя | Ожидаемый результат |
|---|---|---|
| S1 | «Под api в namespace payments в CrashLoopBackOff» | Причина по логам/событиям (например, отсутствует переменная окружения), предложенный патч |
| S2 | «Сервис отдаёт 502 после релиза» | Связка ingress → service → endpoints → поды, найден OOMKilled или неготовые readiness-пробы |
| S3 | «Deployment не раскатывается, зависли 2 из 5 подов» | Причина: Pending из-за нехватки ресурсов/nodeSelector/PVC, предложение |
| S4 | «Почему job не завершается» | Анализ backoffLimit, логов, зависших init-контейнеров |
| S5 | Повтор ранее решённого инцидента | Система находит похожий случай в долгосрочной памяти и ссылается на него |
| S6 | Запрос вне компетенции («напиши стих») | Вежливый отказ, без вызова инструментов кластера |

## 3. Функциональные требования

- **F1. Роутинг.** Оркестратор классифицирует запрос (диагностика / вопрос по runbook / вне области) и выбирает маршрут.
- **F2. Планирование.** Для диагностики строится план из шагов, план хранится в состоянии и корректируется по ходу.
- **F3. Сбор фактов.** Диагност вызывает только read-only инструменты кластера. Каждый результат сохраняется как «свидетельство» с id.
- **F4. Анализ.** Аналитик формулирует гипотезы, каждая гипотеза ссылается на id свидетельств. Аналитик запрашивает у памяти похожие инциденты.
- **F5. Ревью.** Ревьюер проверяет отчёт: нет утверждений без свидетельств, причина объясняет все симптомы. Может вернуть задачу диагносту (максимум 2 итерации).
- **F6. Human-in-the-loop.** Предложенное исправление показывается пользователю; выполнение только после подтверждения через прерывание графа.
- **F7. Исполнение.** Исполнитель применяет подтверждённый патч отдельным набором прав и делает проверку после применения.
- **F8. Память.** После завершения инцидент записывается в долгосрочную память: симптомы, причина, фикс, затронутые объекты, дата.
- **F9. Скиллы.** Типовые расследования описаны файлами-скиллами; оркестратор подключает релевантный скилл к контексту диагноста.
- **F10. Отчёт.** Итог в фиксированном формате: симптомы, свидетельства, причина, исправление, ссылки на прошлые инциденты, потраченные ресурсы.

## 4. Нефункциональные требования

- **N1. Безопасность.** Диагностический контур имеет ServiceAccount с правами только на чтение. Исполнитель имеет отдельный SA с правами patch на ограниченный набор ресурсов. Секреты кластера в контекст LLM не попадают (значения Secret маскируются на уровне инструмента).
- **N2. Изоляция.** Агент запускается в контейнере без root, с read-only файловой системой, без capabilities, сетевой доступ только к LLM API и API-серверу кластера.
- **N3. Производительность.** Типовой инцидент (S1–S4) укладывается в 3 минуты и 15 вызовов инструментов.
  Оба числа — стартовые: 15 вызовов покрывают полный обход одного сценария (поды, события, логи, манифест,
  история релизов) с запасом на одну неудачную ветку, 3 минуты — верхняя граница, при которой инженер ещё
  ждёт ответ, а не уходит разбираться руками. Значения живут в `config.budget` и калибруются по evals;
  все остальные документы ссылаются на конфиг, а не повторяют цифры.
- **N4. Стоимость.** Средняя стоимость инцидента фиксируется в трейсе; порог алерта задаётся конфигом.
- **N5. Наблюдаемость.** Каждый запуск оставляет трейс со всеми вызовами LLM и инструментов, метрики экспортируются в Prometheus, алерты уходят в мессенджер.
- **N6. Воспроизводимость.** Все зависимости зафиксированы, кластер для демо и evals поднимается одной командой (kind).
- **N7. Заменяемость LLM.** Модель задаётся конфигом; любая OpenAI-совместимая модель с tool calling подключается без изменения кода.

## 5. Архитектура (обзор)

Паттерн: **супервизор с графом состояний** (orchestrator-workers) и циклом ревью.
Подробные C4-диаграммы и sequence-диаграмма выносятся в `docs/ARCHITECTURE.md`.

Агенты и их роли:

| Агент | Задача | Инструменты | Модель |
|---|---|---|---|
| Orchestrator | классификация запроса, план, роутинг, финальный отчёт | нет (только память состояния) | основная |
| Diagnostician | сбор фактов по плану | k8s read-only | основная |
| Analyst | гипотезы, поиск похожих инцидентов | memory search, runbook search | основная |
| Reviewer | проверка обоснованности, возврат на доработку | нет | основная или более сильная |
| Executor | применение подтверждённого патча, пост-проверка | k8s patch (ограниченный) | основная |

Общее состояние графа: запрос, план, список свидетельств, гипотезы, черновик отчёта, счётчик итераций,
предложенный патч, статус подтверждения.

Флоу: запрос → Orchestrator (classify) → [Diagnostician ⇄ Analyst] → Reviewer → (назад к Diagnostician | к пользователю)
→ подтверждение → Executor → запись в память → отчёт.

## 6. Инструменты (tools)

Read-only (Diagnostician):

- `k8s_list_pods(namespace, selector)`
- `k8s_describe(kind, name, namespace)`
- `k8s_events(namespace, object)`
- `k8s_logs(pod, container, tail, previous)`
- `k8s_rollout_history(deployment, namespace)`
- `k8s_get_manifest(kind, name, namespace)` с маскированием секретов
- `k8s_top(namespace)` при наличии metrics-server

Память и знания (Analyst):

- `memory_search_incidents(query, filters)`
- `runbook_lookup(topic)`

Исполнение (Executor, только после подтверждения):

- `k8s_patch(kind, name, namespace, patch)` с allow-list ресурсов
- `k8s_rollout_restart(deployment, namespace)`

Каждый инструмент возвращает структурированный результат и id свидетельства; сырой вывод обрезается до лимита.

## 7. Скиллы и семантические файлы

Скиллы лежат в `skills/<name>/SKILL.md` с фронтматтером (name, description, triggers, tools) и телом-инструкцией:

- `crashloop-diagnosis`, `oom-analysis`, `pending-pod`, `ingress-502`, `stuck-job`, `post-release-checklist`.

Семантические файлы в `agent/`:

- `SOUL.md`: принципы поведения (никаких утверждений без свидетельств, безопасность важнее скорости, признавать неопределённость).
- `IDENTITY.md`: кто агент, для кого работает, границы компетенции.
- `MEMORY.md`: правила, что и как запоминать, что запрещено сохранять.
- `RUNBOOKS/*.md`: знания о типовых поломках, читаются Analyst'ом.

## 8. Память

Три слоя:

1. **Рабочая (краткосрочная).** Состояние графа за один инцидент плюс чекпоинтер (SQLite) для восстановления после прерывания и human-in-the-loop. История сообщений сжимается сводкой при превышении бюджета контекста.
2. **Эпизодическая (долгосрочная).** Хранилище прошлых инцидентов: структурированная запись + текст. Гибридный поиск: BM25 (SQLite FTS5) + локальные эмбеддинги (bge-m3 на CPU) + фильтры по namespace/kind + переранжирование LLM. Запись делается после закрытия инцидента с извлечением фактов моделью.
3. **Семантическая и процедурная.** Markdown-файлы (SOUL, runbooks, skills). Выбор релевантного раздела по оглавлению через LLM (подход PageIndex), без векторов.

Почему не «просто RAG»: плоское разбиение на чанки теряет структуру инцидента, не учитывает время
(фикс мог устареть), даёт ложные совпадения по общим словам вроде «pod» и не различает симптом и причину.
Отсюда гибридный поиск, структурные фильтры и переранжирование.

Путь апгрейда: темпоральный граф знаний (Graphiti + FalkorDB), связывающий объекты кластера, инциденты и фиксы во времени.
Сравнение вариантов (Mem0, Letta, LangMem, Cognee, Graphiti, memU, PageIndex, Zep) с недостатками каждого выносится в `docs/MEMORY.md`.

Ограничение среды: `/embeddings` в доступном API закрыт (403), поэтому эмбеддинги считаются локально.

## 9. Изоляция

Выбранная связка: Docker-контейнер (non-root, read-only rootfs, `cap-drop ALL`, ограничение egress) + kind-кластер как цель
+ RBAC с двумя ServiceAccount. Рассмотренные альтернативы и причины отказа (VM, gVisor, Firecracker, E2B, Docker sandbox)
описываются в `docs/ISOLATION.md`. gVisor допускается как дополнительный runtime при наличии.

## 10. Оценка (evals)

Уровни:

- **Модель.** Сравнение минимум четырёх открытых моделей на одном наборе задач: корректность tool calling, следование формату, стоимость, латентность.
- **Компоненты.** Юнит-тесты инструментов и парсеров; тест роутера на наборе запросов с известным классом.
- **Система.** Набор синтетических инцидентов на kind с известной корневой причиной (по 3–5 на сценарии S1–S5, плюс S6).

Метрики системы:

| Метрика | Как считается |
|---|---|
| Root-cause accuracy | совпадение с эталонной причиной (LLM-judge + ручная разметка) |
| Groundedness | доля утверждений отчёта, подкреплённых свидетельствами |
| Tool precision | доля полезных вызовов инструментов от общего числа |
| Steps / latency / cost | из трейсов |
| Safety | ноль мутаций без подтверждения, ноль утечек секретов |
| Refusal accuracy | доля корректных отказов на S6 |

Судья: более сильная проприетарная модель из того же API (используется только в evals).
Запуск: локально командой и в CI на каждый PR; результаты пишутся в Langfuse как scores, тренд смотрится на дашборде.

Формулы метрик, пороги приёмки, состав датасета и меры против перекосов судьи — в `docs/EVALS.md`.

## 11. Наблюдаемость

- **Трейсы LLM и агентов:** Langfuse (self-hosted), интеграция через callback LangGraph.
- **Метрики:** Prometheus (число запусков, длительность, токены, стоимость, итерации ревью, ошибки инструментов, доля отказов).
- **Логи:** структурированный JSON в stdout, сбор в Loki.
- **Алертинг:** Alertmanager → Telegram/Slack. Примеры правил: p95 длительности выше порога, стоимость инцидента выше порога, рост доли ошибок инструментов, зацикливание (итерации ревью = максимум).
- **Специфика агента:** трекинг по шагам графа, а не по HTTP-запросу; учёт стоимости; оценка качества как метрика (scores из evals).

Список метрик, структура трейса, правила алертов и состав дашборда — в `docs/OBSERVABILITY.md`.

| Слой | Выбор | Почему | Что рассматривали |
|---|---|---|---|

| LLM | открытые модели через OpenAI-совместимый API из `local.env`; актуальный список кандидатов, протокол сравнения и результаты — `docs/LLM_SELECTION.md` | сравнение всех кандидатов по одному протоколу, финальный выбор по evals | проприетарные модели только как judge |
| Движок | внешний OpenAI-совместимый шлюз; fallback vLLM в docker-compose | контракт API одинаковый, код не меняется; vLLM показывает, как система живёт полностью локально | Ollama (удобен, но слабее по throughput и батчингу), llama.cpp (CPU/edge, нет нужды) |
| Фреймворк | LangGraph | явный граф состояния, циклы, роутинг, чекпоинтер, прерывания для human-in-the-loop, интеграция с Langfuse | CrewAI (ролевой, слабее контроль циклов и состояния), AutoGen (диалоговая модель, роутинг менее детерминирован), Haystack (ориентирован на RAG-пайплайны), AutoGPT (платформа, а не библиотека), чистый LangChain (нет графа состояний) |
| Память | SQLite FTS5 + локальные эмбеддинги bge-m3 + LLM rerank; Markdown-знания с навигацией по оглавлению; путь апгрейда Graphiti | работает без внешних сервисов эмбеддингов, учитывает структуру и время | Mem0/Zep (нужны эмбеддинги через API), Letta (свой рантайм агентов, конфликт с LangGraph), Cognee (тяжёлая ingest-пайплайн) |
| Изоляция | Docker hardened + RBAC + kind | достаточная граница для read-only агента, воспроизводимо на ноутбуке | VM/Firecracker (избыточно для v1), gVisor (опционально) |
| Наблюдаемость | Langfuse + Prometheus/Grafana/Loki/Alertmanager | LLM-native трейсы плюс привычный SRE-стек | LangSmith (SaaS), Langtrace, Phoenix (легче, но без scores-пайплайна) |
| Evals | pytest + собственный harness + Langfuse scores; judge через тот же API | воспроизводимо и в CI | DeepEval, RAGAS (рассматриваются для метрик groundedness) |
| Демо-окружение | kind + набор «сломанных» манифестов | одна команда для стенда и для evals | minikube, k3d |

## 13. Риски

- Langfuse self-hosted тяжёлый по компонентам; при проблемах заменить на Phoenix, метрики и алерты не пострадают.
- Открытые модели могут нестабильно соблюдать формат; мит.: structured output через pydantic и повтор с валидацией.
- Локальные эмбеддинги на CPU медленны при большой базе; для v1 база малая, далее квантизация или отдельный сервис.
- Извлечение фактов в память моделью может ошибаться; мит.: ревью записи перед сохранением, версионирование.
