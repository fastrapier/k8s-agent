# 0002. Два контура и две учётки: диагност только читает, исполнитель — отдельно

**Статус:** Принято, дата 2026-10-10

## Контекст

Диагност читает логи, события и манифесты, но не должен менять кластер.
Исправление требует отдельной границы прав и явного действия человека.
Один ServiceAccount смешал бы чтение и запись и сделал бы ошибку модели мутацией.
RBAC должен ограничивать и модель угроз, и случайный импорт кода записи.

## Решение

Диагностический контур работает под `incident-agent-ro`.
Его ClusterRole содержит только нужные `get`/`list` и не даёт доступа к Secret.
Исполнитель работает под `incident-agent-rw`.
Его Role ограничена namespace `payments` и операциями patch на разрешённых объектах.
Весь код записи находится в `executor.py` и строит отдельный RW-клиент.
Набор инструментов диагноста формируется из `READONLY_TOOLS`; `k8s_patch` туда не входит.
Перед записью граф проходит узел `approval`, который вызывает `interrupt()`.
Продолжение возможно только внешним `resume` с решением человека.
`execute` дополнительно проверяет `approval_status == "approved"`.

## Последствия

Плюсы:
- ошибка модели в диагностике не получает права записи;
- RBAC и код дают независимые рубежи;
- решение человека является отдельным событием графа;
- проверка импортов ловит втягивание исполнителя в read-only контур.

Цена:
- два kubeconfig и выпуск токенов нужно поддерживать на стенде;
- подтверждение добавляет паузу и ручной шаг в demo;
- исполнителю всё равно нужна дополнительная валидация патча.

## Отвергнутые варианты

- **Один ServiceAccount с patch** — компрометация диагноста сразу становится мутацией.
- **Флаг `approved` в состоянии** — модель или ошибочный узел мог бы выставить его сама.
- **Подтверждение в тексте отчёта** — текст не блокирует вызов API и не является барьером.
