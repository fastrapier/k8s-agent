# 0007. Эпизодическая память: SQLite + FTS5 без эмбеддингов

**Статус:** Принято, дата 2026-10-10

## Контекст

S5 требует находить прошлые инциденты и отличать тот же класс поломки от похожего текста.
Память должна работать локально, быть воспроизводимой и не отправлять эмбеддинги наружу.
Ограничение контейнера — 512 МиБ, тогда как веса bge-m3 занимают около 2.2 ГБ.
Запись должна сохранять проверенную причину и фактический фикс, а не пересказ модели.

## Решение

Долгосрочное хранилище — SQLite с виртуальной таблицей SQLite FTS5.
Поиск строится BM25 с префиксами слов, фильтром namespace и штрафом старых записей.
Записи получают id вида `inc-YYYY-MM-DD-NNN`.
В таблице хранятся симптомы, причина, фикс, затронутые объекты, evidence ids и `trace_id`.
`MemoryStore.write` вызывается из `remember` после ревью.
Причина берётся из первой проверенной гипотезы аналитика.
Код фикса собирается каноническим JSON из предложенного и применённого патча.
В поиск попадают только записи с разрешённым исходом; `unresolved` исключается.
Дубликаты одного объекта и фикса связываются через `superseded_by`.
Путь апгрейда — локальный темпоральный граф Graphiti + FalkorDB.

## Последствия

Плюсы:
- память помещается в контейнер и не требует внешнего embedding API;
- поиск объясним через FTS5, фильтры и дату;
- источник записи детерминирован кодом и evidence ids;
- устаревший фикс получает штраф, а не исчезает бесследно.

Цена:
- BM25 хуже понимает смысловые перефразировки без общих слов;
- модель всё ещё оценивает `same_class` и отличие найденного кейса;
- SQLite не является распределённым хранилищем для нескольких кластеров.

## Отвергнутые варианты

- **bge-m3 в контейнере** — веса превышают лимит памяти примерно в четыре раза.
- **Внешние embeddings** — доступный `/embeddings` закрыт 403 и возникла бы утечка данных.
- **Mem0/Letta/Cognee сразу** — лишний runtime и ingest-пайплайн для v1.
