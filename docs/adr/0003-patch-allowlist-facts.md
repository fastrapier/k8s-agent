# 0003. Белый список патча и привязка патча к фактам

**Статус:** Принято, дата 2026-10-10

## Контекст

Даже подтверждённый человеком патч может адресовать не тот объект или опасное поле.
Модель видит логи и может выбрать соседний Deployment по похожему имени.
Strategic merge допускает `null` и специальные `$`-директивы с разрушающей семантикой.
Ревью М4 выявило необходимость проверять цель и свежесть объекта кодом.

## Решение

Разрешены только `Deployment`, `StatefulSet` и `ConfigMap` в namespace `payments`.
Пути задаются `ALLOWED_PATHS`, а не списком запрещённых исключений.
Разрешены env, resources, replicas, аннотации шаблона и `ConfigMap.data`.
Каждый контейнер в патче обязан иметь имя; неизвестный контейнер отклоняется.
`null`, ключи, начинающиеся с `$`, и пустой патч запрещены.
`spec.replicas` должен быть целым числом не меньше 1.
`_ground` требует ссылки патча только на существующие `ev-NNN`.
Манифест целевого объекта должен быть прочитан этим же прогоном.
Из его metadata берутся `uid` и `generation`; `apply_patch` сверяет их перед записью.
Ссылки на Secret/ConfigMap разрешены только если объект встречался в прочитанных манифестах.

## Последствия

Плюсы:
- неизвестное поле не проходит молча;
- патч нельзя перенаправить на соседний объект;
- устаревший объект даёт статус `stale`, а не запись;
- правило `replicas >= 1` не позволяет «чинить» сбой выключением сервиса.

Цена:
- некоторые легитимные Kubernetes-поля требуют явного расширения allowlist;
- перед предложением патча нужен дополнительный `k8s_get_manifest`;
- при изменении объекта между показом и подтверждением нужен новый прогон.

## Отвергнутые варианты

- **Чёрный список опасных полей** — новое поле могло бы пройти без ревью.
- **Проверка только моделью** — prompt и ответ не являются исполняемым контролем.
- **Патч без uid/generation** — подтверждение могло бы относиться к уже изменённому объекту.
