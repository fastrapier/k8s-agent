# 0006. Structured output: json_schema для закрытых схем, json_object для патча

**Статус:** Принято, дата 2026-10-10

## Контекст

Узлы графа передают модели маршруты, план, гипотезы, вердикты и патч.
Pydantic-схемы запрещают лишние поля и проверяют ссылки на свидетельства.
Для закрытых объектов шлюз умеет принудительный `json_schema`.
Для патча поле `dict[str, Any]` открытое, и DEFENSE М4 зафиксировал зависание декодирования.

## Решение

`LLMClient.structured` использует `json_schema` для закрытых схем.
В запрос передаётся имя схемы и `model_json_schema()`.
Для схемы с открытым объектом патча используется `response_format: json_object`.
Та же JSON-схема добавляется в системный промпт обычным текстом.
Ответ затем разбирается `parse_json` и валидируется Pydantic.
При JSON-ошибке или `ValidationError` выполняется до двух повторов.
В повтор модель получает сжатый текст ошибки валидации.
Патч дополнительно проверяется белым списком и привязкой к фактам в коде.
Закрытые схемы маршрута, плана и ревью остаются на `json_schema`.

## Последствия

Плюсы:
- закрытые контракты получают проверку шлюза до Pydantic;
- открытый patch-объект не провоцирует бесконечные пробелы;
- причина повтора видна в Usage и трейсе;
- структурная валидация не заменяется доверием к тексту модели.

Цена:
- у patch-схемы часть дисциплины переносится в промпт и постпроверки;
- до трёх HTTP-вызовов увеличивают задержку и стоимость;
- разные режимы ответа нужно поддерживать в одном клиенте.

## Отвергнутые варианты

- **Всегда `json_schema`** — на открытом patch-объекте шлюз зацикливался пробелами.
- **Всегда `json_object` без схемы** — модель могла бы вернуть неверные поля и типы.
- **Принимать JSON без Pydantic** — ошибки контракта дошли бы до следующего узла графа.
