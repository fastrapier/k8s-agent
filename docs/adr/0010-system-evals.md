# 0010. Системные evals: граф до approval, судья gpt-5.5, память кейса в ОЗУ

**Статус:** Принято, дата 2026-10-10

## Контекст

Модельные блоки М3 не проверяют полный цикл графа и безопасность применения патча.
М8 требует кейсы S1–S6, groundedness, root-cause accuracy, отказ и память.
Evals не должны чинить стенд для следующего кейса и не должны загрязнять память автора.
Для оценки нужен независимый судья, но шлюз ограничивает доступные имена моделей.

## Решение

Системный harness прогоняет граф каждого кейса до `approval`.
На approval harness передаёт отказ, поэтому стенд не мутирует.
Для каждого кейса создаётся собственный `MemoryStore` в ОЗУ.
Фикстура памяти загружается только явно запрошенным кейсом S5.
Вариации v1 — это разные формулировки жалобы на одних и тех же поломках.
Главные метрики: root-cause accuracy, groundedness, safety, refusal и memory hit rate.
Судья — `gpt-5.5` по принятому протоколу; имена `sub/claude-*` на ключе шлюза отвечают 401.
Судья получает структурированный ответ и используется только в evals.
Flash-кандидат решается по системному прогону, а не по одиночной таблице М3.

## Последствия

Плюсы:
- каждый кейс безопасен для следующего и повторяем локально;
- отказ на approval проверяет путь до подтверждения без мутации;
- память и трасса изолированы, результаты сопоставимы;
- judge измеряет groundedness и причину отдельно от рабочей модели.

Цена:
- разные формулировки не покрывают разные конфигурации стенда;
- evals требуют токен и стоят денег, поэтому запускаются локально;
- недоступное имя judge нужно явно проверять по 401 и конфигурации шлюза.

## Отвергнутые варианты

- **Применять патчи в evals** — следующий кейс увидел бы уже исправленный кластер.
- **Использовать ту же glm-5.3 как judge** — систематическое согласие модели с собой.
- **Полный набор свежих namespace из EVALS §4.3** — не успевает к защите; путь расширения оставлен.
- **Оценивать отчёты вручную без judge** — нерепродуцируемо для 18 кейсов и нескольких запусков.
